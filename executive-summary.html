Forensic interpretation · cautious

Why H33-2-B2 may have led the historical list

The portfolio report describes H33-2-B2 as a sparse descendant of the H19-5 lineament field, created by removing predictions close to the mapped-fault catalogue. This is a pruning strategy, not an independent new detector. The file audit describes a two-pixel catalogue-flank deletion; that is artifact metadata, not a score result.

For the task metric stated in the request (alpha 0.2, beta 0.8, and a 300 m triangular distance kernel), a candidate dot is useful only when it adds enough marginal distance-kernel credit to justify its false-positive mass. Neighboring dots can have strongly overlapping kernel support. Removing low-marginal-credit or redundant dots can therefore improve a score while preserving much of the spatial coverage. Conversely, pruning true hidden faults increases the miss penalty; the sign of that tradeoff must be measured on a leakage-safe spatial holdout.

This mechanism is plausible, not proven. The exact score-to-file receipt and hidden test truth are unavailable here. Historical catalogue buffers must also be rebuilt fold-locally in any future holdout; a full-catalogue mask must not leak into the withheld fold.

Could a unique candidate beat the historical leader?

It is possible in principle but cannot be estimated or guaranteed from this checkout. The reviewed portfolio report indicates that the apparent leaders share a pruning lineage, so merely re-encoding, thinning, or ensembling those masks is not a new discovery. A defensible attempt needs a different off-catalogue signal and a better spatially blocked HOLDOUT-DTI result. No such result or submission file exists here.

Decision

No claim that a fresh candidate beats the historical entry.

The independent-looking top entries are reported to share substantial raster lineage: GEMSDOE25 and GEMSDOE30 are described as mask-identical; GEMSDOE31 and GEMSDOE28 sit in the same pruning family; GEMSDOE36 is reported as a superset of GEMSDOE32. Ensembling these as independent discoveries would double-count one hypothesis family.

Every one of the nine historical files is marked not unique / do not submit in the portfolio review. These findings are cited, not freshly recomputed here.

When a future file is promoted

How to submit safely

  1. Check the release banner. Proceed only if it explicitly says “OK TO DOWNLOAD AND SUBMIT.” A research-only, format-only, or holdout-only file is not cleared.
  2. Download the project’s promoted GeoTIFF. Confirm its SHA-256 and run-card link match the release record. Do not use a historical file from another GEMSDOE site as a replacement.
  3. Check the file format. The competition’s submission instructions specify one single-band GeoTIFF (or a ZIP with one GeoTIFF) matching the sample’s CRS, shape, and geotransform. Validate prediction values in [0, 1], with no NaN inside the scoring footprint, before upload.
  4. Open the official competition submission page. Select the TIFF and enter a unique submission name and a short note (at most 140 characters under this project’s run-card convention). The competition website, not this site, determines whether the upload is accepted.
  5. Save the receipt and exact bytes. Store the organizer’s receipt and tie it to the submitted raster SHA-256. Only that receipt supports the `ORGANIZER-CONFIRMED` label.
Current situation: there is no promoted file and no download action. The upload flow also requires an authenticated DrivenData account; this project has no credentials and will not ask you to place secrets in chat or source control.

Irregularities and blockers

What must be resolved before an experiment

  • Starter checkout only: no data, sample template, model code, shared evaluator/writer, feature cache, or registry rasters are tracked here.
  • Lane ambiguity: the request requires one designated method paragraph, but does not identify one unambiguously. No lane was inferred.
  • Historical score provenance: the reviewed internal portfolio report says the scores are owner-reported and not linked to organizer receipts for exact files.
  • Leaderboard conflict: the request contains inconsistent, undated “current high score” claims. No live leaderboard read was possible; no value is adopted.
  • Network and auth: the execution environment can reach GitHub and package registries, not the competition, USGS, NASA, NLR, or other external source hosts. DrivenData authentication is unavailable.
  • Toolchain: geospatial/scientific Python packages were absent; no TIFF was opened or raster metric calculated in this checkout.

Final decision

Negative: no artifact promoted.
