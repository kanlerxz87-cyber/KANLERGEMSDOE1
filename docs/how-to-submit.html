The “Predicted values must be in range [0, 1]” error — root causes and the fix

The portal rejects a file with that message in exactly the situations our validator now reproduces and blocks locally:

  1. Mode A — NaN inside the footprint. NaN fails every 0 ≤ x ≤ 1 comparison. (NaN outside the footprint is the official sample's own encoding and is legal per the format spec: “data outside the bounds is null or nan”.)
  2. Mode B — a finite value outside [0,1], classically a leftover -3.4e38 float32 nodata sentinel from the training stack, or unclipped probabilities > 1.

Fix (guaranteed by construction here): submit the -zeros.tif variant — finite everywhere, 0.0 outside the footprint, no nodata sentinel — produced only by the shared writer (scripts/submission_writer.py), which rejects non-finite/out-of-range input instead of clipping it, then re-opens the written bytes and audits: single band, float32, EPSG:32611, 3730×3292, exact transform vs the template, 5,167,373/5,167,373 finite footprint pixels, min 0.0 / max 1.0, zero positives on the catalogue. Independent re-audit of this session's files: all PASS (receipt). If the portal still rejects a -zeros file that passes locally, upload the one-file .zip twin and record the exact portal message — do not silently edit values.
