How to submit a GEMS GeoTIFF

This is the portal workflow and preflight standard, not authorization to upload. A file is uploadable only after the scientific selector separately approves it. At this review, there is no validated TIFF to download or submit.

Current state: NO FILE APPROVED · NO DOWNLOAD LINK · DO NOT SUBMIT. No candidate raster, template, or local validation receipt exists in this checkout. The historical GEMSDOE32 H33-B2 file is a previous claimed submission and must not be copied, renamed, or re-uploaded as a new candidate.

Before opening the portal

Automated gates — all must pass

  1. Freeze the scientific experiment.

    Use the selected lane and shared `evaluate_holdout.py`/`submission_writer.py`. The evaluator must hide whole fault segments with a buffer, build catalogue-derived features from visible faults only, mask visible faults pixel-exactly, and score pooled DTI using alpha 0.2, beta 0.8, and the 300 m triangular kernel. Report `HOLDOUT-DTI`, evaluator version, withheld-positive count, and 95% CI. Do not translate this to a leaderboard forecast.

  2. Pass leakage canaries.

    Test each feature alone before trusting the model. Under the supplied protocol, a single-feature AUC above 0.90 is a stop until leakage is ruled out. Confirm every catalogue-derived feature was generated fold-locally from visible faults.

  3. Pass both uniqueness checks.

    Compare the candidate surface before placement and final dots against the full frozen registry. Stop if absolute rank-correlation exceeds 0.90 or more than 70% of candidate dots lie within 3 pixels of any one registry raster. Record the registry snapshot, nearest raster, and both pre-placement/final measurements.

  4. Validate the saved file against the actual sample template.

    Use the official sample-submission grid, not a guessed width/height or another team's raster. Require one GeoTIFF band, `float32`, EPSG:32611, matching shape, bounds, resolution, and affine transform. Confirm every valid in-footprint pixel is finite and in `[0,1]`; nonfinite/nodata cells must be outside the valid footprint, consistent with the competition specification. Reopen the TIFF after writing and validate the bytes that will be uploaded.

  5. Issue a complete run card.

    Include the hypothesis, mechanism, a named non-fault mimic, holdout result and CI, registry comparisons, SHA-256, technical validator output, a unique portal name, a note of at most 140 characters, and a `promote` or `negative` verdict. A failed or incomplete gate means research-only, not uploadable.

  6. Make a separate slot decision.

    The supplied protocol explicitly separates promotion to a competition slot from experimentation. Check the current submission-page quota/cap yourself; this project has not selected or spent a slot. The official challenge description says competitors choose one submission for scoring across both prize rounds before the deadline.

Portal actions

Once—and only once—the file is approved

  1. Open the official competition page and sign in.

    Go to DrivenData · DOE GEMS, then open the competition's submission area. The competition data page redirected to login in this review environment; no automated account access or portal submission was performed.

  2. Choose the exact approved file.

    In “New submission,” select the one approved `.tif`. The portal text quoted in the project brief also says it accepts a `.zip` containing one GeoTIFF; re-check the live form before relying on that alternative. Do not select a report, sidecar, NaN/zero twin, or a historical source-site TIFF.

  3. Enter a unique name and short note.

    Use the name and note bound to the run card. Keep the note at or below 140 characters for this project and ensure it says what distinguishes this experiment. Example template only (not an approval): GEMS <lane> <mechanism> | HOLDOUT-DTI <value> n=<count> | <id>. Do not invent a value or call a holdout result a leaderboard score.

  4. Review the portal receipt after uploading.

    Only a submission-page receipt that identifies the submission and score can establish an `ORGANIZER-CONFIRMED` result under this project's evidence policy. Preserve the receipt, exact filename, SHA-256, portal name/note, and time. Do not infer acceptance from a local format pass.

Prevent the range error

“Predicted values must be in range [0, 1]”

The error text alone does not identify the cause. This checkout has no failed TIFF to inspect, so the cause is unresolved. Before a future upload, reopen the written file and check all in-footprint prediction values—not just the model output or a display-scaled image.

  • Verify finite in-footprint minimum is at least 0 and maximum at most 1; catch negative values, values above 1, and infinities.
  • Check the nodata mask against the sample template. A numeric nodata sentinel such as a large negative value must not be treated as an ordinary prediction inside the valid footprint.
  • Check for NaN inside the footprint. The official page specifies null/NaN outside bounds; do not use outside-bound values that violate the template's mask or the portal's range check.
  • Reopen the exact `.tif` after saving, read the stored band and metadata, then recompute the minimum/maximum over the valid footprint.
  • Keep the validator output and TIFF SHA-256 with the run card. If the portal still rejects the file, preserve the exact error/receipt and do not silently change the array.

The competition's official format requires one `float32` layer, EPSG:32611, the same grid/bounds/resolution, in-footprint predictions in [0,1], and null/NaN outside the bounds. The live template and portal remain authoritative for a future upload.
