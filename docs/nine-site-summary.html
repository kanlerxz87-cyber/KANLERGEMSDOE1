5. Irregularities flagged for review

  1. B1 — labels identity (blocker, from main's review). labels.tif and existing_faults.tif are byte-identical (60,988 positives each). The SGMC-CAL proxy in this page is defined relative to labels.tif, so every HOLDOUT-DTI value here is provisional until the labels are verified against the official download. See evidence/label_integrity_20261031.json.
  2. Literal 3-px uniqueness rule is saturated by dense references (main's review: no exemption authorized). The r13-lattice reference covers almost the whole footprint at 3 px, so any dense candidate fails the literal rule (ours: 99.98% within 3 px). Exact-pixel Jaccard is 0.0062, so the two dot sets share almost no pixels. Exact-pixel Jaccard is a complementary measure. The literal rule currently fails for this file. Team decision needed. The rule is the one written in the repo's protocol, not a DrivenData rule.
  3. GEMSDOE30 duplicates GEMSDOE25 in dots. (Exact mask equality is computed in section 4.) The ledger ID ends in 91eae1ca, which is GEMSDOE25's SHA prefix, but the pinned GEMSDOE30 file is 8cf893ea. Its bytes differ, but its dots match GEMSDOE25 (exact mask equal: True, dot count 44,090, same SGMC-CAL). Both score 0.2600 USER-REPORTED. Treat GEMSDOE30 as not a distinct submission.
  4. GEMSDOE25 owner-mirror copy is mislabelled. data/scored/gems24-…-e56ea318af89-nan.tif is byte-identical to GEMSDOE25's focus file. The "gems24" name is wrong.
  5. GEMSDOE28 and GEMSDOE31 share a run ID. 8acb75e1 appears in both ledger entries and both score 0.2708. Their dots are nearly identical (3-px overlap 99.8% and 99.6%), though the bytes differ.
  6. Nine-site overlap is high. Many focus files overlap at 95% or more with one another (section 4). The nine are not nine independent placements. Our candidate is the exception among the files checked (max 26% against any focus file, except the r13 lattice).
  7. Champion has three identical copies (GEMSDOE32 focus, registry, and docs/downloads). Expected, but it means the registry is not an independent reference.
  8. Leaderboard top conflicts: the prompt gives 0.4413 and, in another place, 0.3195. The live public leaderboard (2026-10-31) gives 0.4544 for #1, and the repo's 2026-10-29 snapshot agrees. These are PUBLIC-test values. The Initial Prize Round is decided on the PRIVATE test set (see DrivenData competition page).
  9. "Predicted values must be in range [0, 1]" root cause not confirmed. The NaN-outside file passes the local validator. The GEMSDOE32 benchmark is a zeros-outside file that scored, so zeros-outside is not automatically rejected. Only the portal can confirm.
  10. Provenance of competition inputs. training_features.tif, labels.tif and sample_submission.tif come from other teams' GitHub repos (see registry/data_manifest.json), not from DrivenData. Hash pins prove mirror consistency only. Confirm the rules allow this use before relying on them.
  11. Evaluator rejects NaN. Proxy values here come from zeros-outside copies in a temp dir. The same in-footprint values are used. This is a measurement convenience, not a submission.
  12. Sandbox access. DrivenData and the GitHub Pages sites are not reachable from this sandbox. Ledger values could not be re-checked against their source pages.
